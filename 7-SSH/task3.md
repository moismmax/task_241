## Критерий приёмки

В отчёте должны быть:
- команда генерации ключа `ed25519`;
- пути к публичному и приватному ключам;
- команда копирования публичного ключа на сервер;
- путь к `authorized_keys`;
- права на `~/.ssh` и `authorized_keys`;
- фрагмент конфигурации, отключающий парольную аутентификацию;
- подтверждение успешного входа по ключу;
- подтверждение отказа при попытке парольной аутентификации;
- краткое пояснение, почему приватный ключ нельзя передавать другим пользователям.


# Настраиваем SSH-аутентификацию по ключам

## 1. Что такое SSH-ключи и зачем они нужны

SSH-ключи — это пара криптографически связанных ключей, которая используется для безопасной аутентификации при подключении к удалённому серверу.

Пара состоит из двух частей:

- **Приватный ключ** — хранится только у владельца и используется для подтверждения личности. Его нельзя передавать другим пользователям.
- **Публичный ключ** — размещается на сервере и используется для проверки подлинности пользователя.

Аутентификация по ключам позволяет подключаться к серверу без ввода пароля учётной записи. При этом приватный ключ при подключении не передаётся серверу.

## 2. Создание пары SSH-ключей

В macOS используется встроенная утилита `ssh-keygen`.

Создадим ключ типа `ed25519`:

```bash
ssh-keygen -t ed25519 -C "moismmax@MacBook-Air"
```

Во время выполнения команды программа предложит указать путь сохранения ключа. Можно оставить предложенный вариант:

```text
/Users/moismmax/.ssh/id_ed25519
```

Затем программа предложит установить парольную фразу (passphrase) для защиты приватного ключа. Рекомендуется задать её.

## 3. Где хранятся ключи

По умолчанию после генерации создаются два файла:

**Приватный ключ:**

```text
/Users/moismmax/.ssh/id_ed25519
```

**Публичный ключ:**

```text
/Users/moismmax/.ssh/id_ed25519.pub
```

Посмотреть содержимое каталога:

```bash
ls -la ~/.ssh
```

Посмотреть публичный ключ:

```bash
cat ~/.ssh/id_ed25519.pub
```

Приватный ключ нельзя публиковать, отправлять другим пользователям или размещать в общедоступных хранилищах.

## 4. Копирование публичного ключа на сервер

В macOS можно использовать команду `ssh-copy-id`, если эта утилита установлена.

Поскольку она может отсутствовать в стандартной поставке macOS, можно воспользоваться альтернативным способом:

```bash
cat ~/.ssh/id_ed25519.pub | ssh myserver 'umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys; chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys'
```

Здесь `myserver` — псевдоним сервера, настроенный ранее в `~/.ssh/config`.

Публичный ключ добавляется в файл:

```text
~/.ssh/authorized_keys
```

Полный путь на удалённом сервере для пользователя `ssh-user` обычно выглядит так:

```text
/home/ssh-user/.ssh/authorized_keys
```

Для пользователя `root`:

```text
/root/.ssh/authorized_keys
```

На macOS-сервере домашний каталог пользователя может находиться в `/Users/имя_пользователя`.

## 5. Подключение к серверу по ключу

После копирования публичного ключа выполняем подключение:

```bash
ssh myserver
```

Если ключ настроен правильно, сервер проверит его и разрешит вход.

При использовании приватного ключа с passphrase может запрашиваться парольная фраза самого ключа. Это не пароль учётной записи на сервере.

Проверить, какой метод аутентификации используется, можно с подробным выводом:

```bash
ssh -v myserver
```

В выводе ищем сообщения, связанные с `Offering public key` и `Authenticated using "publickey"`.

## 6. Проверка прав доступа

На удалённом Linux-сервере необходимо проверить права на каталог и файл:

```bash
ls -ld ~/.ssh
ls -l ~/.ssh/authorized_keys
```

Рекомендуемые права:

Для каталога `.ssh`:

```text
700
```

Для файла `authorized_keys`:

```text
600
```

Установить права можно командами:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

Владелец каталога и файла должен совпадать с пользователем, под которым выполняется подключение.

## 7. Запрет парольной SSH-аутентификации

Для отключения парольной аутентификации необходимо изменить конфигурацию SSH-сервера.

На Linux открыть файл:

```bash
sudo nano /etc/ssh/sshd_config
```

Добавить или изменить параметры:

```text
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
```

Первый параметр разрешает вход по публичному ключу.

Второй отключает аутентификацию обычным паролем.

Третий отключает интерактивную аутентификацию, которая в некоторых конфигурациях может использоваться для запроса пароля.

Важно: если сервер использует PAM или дополнительные механизмы аутентификации, необходимо проверить их настройки отдельно.

Проверить конфигурацию:

```bash
sudo sshd -t
```

Посмотреть действующие параметры:

```bash
sudo sshd -T | grep -E 'pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication'
```

Ожидаемые значения:

```text
pubkeyauthentication yes
passwordauthentication no
kbdinteractiveauthentication no
```

После успешной проверки перезапустить SSH-службу:

```bash
sudo systemctl restart ssh
```

На некоторых Linux-системах:

```bash
sudo systemctl restart sshd
```

**Важно:** перед отключением парольной аутентификации необходимо убедиться, что вход по ключу работает. Текущую SSH-сессию следует оставить открытой, чтобы не потерять доступ к серверу.

На macOS-сервере используется тот же файл `/etc/ssh/sshd_config`, но управление службой осуществляется через `launchd`, а не `systemctl`.

## 8. Проверка входа по ключу во второй консоли

Не закрывая текущую SSH-сессию, открываем второе окно терминала macOS.

Выполняем:

```bash
ssh myserver
```

Если подключение прошло успешно и сервер использовал публичный ключ, значит вход по ключу работает.

Для дополнительной проверки:

```bash
ssh -v myserver
```

В подробном выводе необходимо найти подтверждение успешной аутентификации по публичному ключу.

## 9. Проверка запрета парольной аутентификации

На клиенте можно принудительно отключить использование ключей и попробовать подключиться только с паролем:

```bash
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password -o NumberOfPasswordPrompts=1 myserver
```

Если парольная аутентификация на сервере отключена, сервер должен отказать в таком способе входа.

Проверить действующие настройки на сервере:

```bash
sudo sshd -T | grep passwordauthentication
```

Ожидаемый результат:

```text
passwordauthentication no
```

Также проверить интерактивную аутентификацию:

```bash
sudo sshd -T | grep kbdinteractiveauthentication
```

Ожидаемый результат:

```text
kbdinteractiveauthentication no
```

## 10. Почему нельзя передавать приватный ключ другим пользователям

Приватный ключ является секретной частью пары SSH-ключей.

Если передать его другому человеку, этот человек потенциально сможет подключаться к серверам от имени владельца ключа.

Это может привести к:
- Несанкционированному доступу к серверам.
- Утечке конфиденциальных данных.
- Выполнению команд от имени владельца учётной записи.
- Потере контроля над доступом к серверу.

Для каждого пользователя рекомендуется создавать собственную пару ключей, а на сервер добавлять соответствующий публичный ключ.

---

## Вывод

SSH-аутентификация по ключам позволяет безопасно подключаться к удалённым серверам без использования пароля учётной записи.

В macOS для создания ключей используется `ssh-keygen -t ed25519`. Приватный ключ хранится в `~/.ssh/id_ed25519`, а публичный — в `~/.ssh/id_ed25519.pub`.

Публичный ключ копируется на сервер в файл `~/.ssh/authorized_keys`. Для безопасной работы каталогу `.ssh` назначаются права `700`, а файлу `authorized_keys` — `600`.

Для отключения парольной аутентификации используются параметры `PasswordAuthentication no` и `KbdInteractiveAuthentication no`. Перед применением изменений необходимо проверить конфигурацию и убедиться, что вход по ключу работает.

**Примечание по macOS:** команды создания ключей, подключения и копирования публичного ключа выполняются непосредственно на Mac. Изменение `/etc/ssh/sshd_config` и отключение парольной аутентификации выполняются на целевом SSH-сервере. Если предоставленный сервер работает под Linux, используются приведённые команды `systemctl`. Фактические результаты подключения и проверки необходимо получить при выполнении команд.
